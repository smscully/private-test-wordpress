# Production WordPress on AWS (EKS + RDS + S3 Offload)

EKS, the WordPress Helm chart, S3 media offload and RDS together make a standard production design for WordPress on AWS. The design alone doesn't make the site production-ready: that comes from how each piece is configured, as described below. The design also adds **AI-generated post summaries**, run as an event-driven, monitored and tested LLM service. Summaries go through an **LLM gateway** that routes between **Amazon Bedrock** models and a **self-hosted model** on dedicated LLM nodes.

The project runs **two separate WordPress sites** from the same code and manifests: **russetleaf.com** on the full AWS design (brought up only for demos) and **russetleaf.dev** on a budget home lab (running 24/7). See [The two sites](#the-two-sites). Changes reach them through **local → ci → staging → prod** environments; see [Environments and promotion](#environments-and-promotion).

Step-by-step build plans: [`homelab-plan.md`](homelab-plan.md) (russetleaf.dev, built first) and [`aws-eks-plan.md`](aws-eks-plan.md) (russetleaf.com, built second).

The project is split across **four Git repositories** (`wp-gitops`, `wp-infra`, `wp-image` and `llm-summarizer`); see [Repository structure](#repository-structure-four-repos) at the end.

## The two sites

The two sites are **fully independent**: each has its own URL, database, cache, media bucket, queues, secrets and content. Nothing is shared at runtime. What they share is how they're built: the same WordPress image (`wp-image`), the same summarizer chart (`llm-summarizer`), the same base manifests (`wp-gitops`) and the same Terraform modules (`wp-infra`). Each site's specifics (domain, endpoints, bucket names, queue URLs, secrets) live in its own overlay and Terraform environment.

## What production-ready adds

### High availability
- **RDS for MariaDB** with **Multi-AZ** turned on. (Aurora doesn't offer MariaDB; if the site outgrew RDS, Aurora MySQL would be the next step, at the cost of switching engines.) **RDS Proxy** in front of it keeps failovers to seconds.
- At least **2–3 WordPress replicas** spread across availability zones, plus a **HorizontalPodAutoscaler** and **PodDisruptionBudgets**.
- EKS worker nodes in **multiple AZs**, provisioned by **Karpenter** (see Delivery and operations).

### Traffic and edge
- **Application Load Balancer** through the AWS Load Balancer Controller, with **TLS certificates from ACM**. Its DNS name (`origin.russetleaf.com`) is managed by **ExternalDNS**.
- **CloudFront** in front of both the site and the S3 media. In this project CloudFront is **always on** (it costs almost nothing idle), so it can show an offline page when the demo stack is down; see [russetleaf.com between demos](#russetleafcom-between-demos).
- **The ALB accepts only CloudFront traffic:** its security group allows only AWS's CloudFront origin-facing IP list, and a listener rule requires a secret header that CloudFront adds to every request.
- **AWS WAF** on the ALB. A 24/7 production site would usually put WAF on CloudFront instead; here it sits on the ALB so it exists (and costs money) only during demos.

### Performance
- **Object cache** (ElastiCache Redis or Valkey) with a Redis object-cache plugin. This cuts database load sharply.
- **PHP OPcache** (enabled in the custom WordPress image).

### Security
- S3, SQS, SES and Bedrock access through **EKS Pod Identity** (IRSA only for any component that doesn't support Pod Identity), not stored AWS access keys. Each role gets only what it needs:
  - WordPress may write to its S3 bucket, send to the queue, and `rds-db:connect` as the `wordpress` user through RDS Proxy.
  - The summarizer may read from the queue; it reaches models only through the gateway.
  - The LLM gateway may call `bedrock:InvokeModel` on the chosen Bedrock models only.
- **No application database password on russetleaf.com:** WordPress logs in to RDS Proxy with IAM auth tokens; the master password is generated and rotated by RDS. At home, MariaDB Operator generates and rotates the passwords. See [Database access and credentials](#database-access-and-credentials).
- Other secrets (API tokens, SMTP credentials, the Slack token) in **AWS Secrets Manager**, synced into the cluster by **External Secrets Operator**.
- **Encryption in transit:** TLS on every sensitive connection, plus Cilium's **WireGuard** encryption for pod traffic between nodes. No service mesh, by a recorded decision; see [Service mesh (Istio): not used, by decision](#service-mesh-istio-not-used-by-decision).
- **CiliumNetworkPolicies** (Cilium on both clusters): default-deny in each application namespace, then only the connections each workload needs (e.g. only WordPress may reach the database), with outbound traffic to AWS allowed **by DNS name**; see [Networking: Cilium and Hubble](#networking-cilium-and-hubble).
- RDS in **private subnets**, with **TLS required** on connections.
- `DISALLOW_FILE_MODS` set to `true` (no plugin or theme installs from the admin screen).

### Supply chain and policy
- CI builds each image, generates an **SBOM** (a list of every package in the image) with **Syft**, scans it with **Trivy**, **signs** it with **cosign** (keyless, using GitHub's OIDC identity), and attaches the SBOM to the image as a **signed attestation** (`cosign attest`, e.g. in SPDX JSON format). The attestation is stored in GHCR next to the image and recorded in Sigstore's transparency log, so anyone can check which packages a given image contains, and that the list came from the project's own CI.
- **Kyverno** policies in the cluster (each named after its equivalent in the official Kyverno policy library):

| Policy | Kyverno equivalent | What it enforces here |
|---|---|---|
| Signed images | Image verification (`verifyImages`, cosign keyless) | Only images signed by the `wp-image` and `llm-summarizer` release workflows run as the project's own workloads; tags are replaced with **digests** at admission (`mutateDigest`), so a re-pushed tag can't change what runs |
| SBOM attestations | Image verification with an `attestations` check | The project's own images must also carry a **signed SBOM attestation** from the same release workflow; an image without one is rejected |
| Signed upstream images | Image verification (`verifyImages`) per upstream publisher | Third-party images from publishers that sign with cosign (e.g. **Kyverno** and **Cilium**; check each upstream's current practice before relying on it) must carry a valid signature from **that publisher's** release identity, so a tampered or substituted upstream image is rejected, not just one from an unknown registry. Images from publishers that don't sign stay covered by the registry allow-list and digest pinning. The list of verified publishers and their identities is kept in the policy, and new entries start in audit mode. Kyverno's own namespace is excluded from these checks, so Kyverno can always start (otherwise it could block itself) |
| Allowed registries | **Restrict Image Registries** (`restrict-image-registries`) | Every container (including init and ephemeral containers) comes from `ghcr.io/<you>/*` or an explicit list of upstream registries used by the platform charts (Cilium, Falco, Argo CD, MariaDB, ...); on EKS, also AWS's own add-on registries |
| No `latest` tag | **Disallow Latest Tag** (`disallow-latest-tag`) | Every image has an explicit tag or digest |
| Required labels | **Require Labels** (`require-labels`), plus a **mutate** rule | Workloads carry `app.kubernetes.io/name`, `app.kubernetes.io/part-of` and `env`; the mutate rule fills in `env` from the namespace, so the validate rule is only a backstop. These labels drive alert routing, OpenCost and policy selectors |
| Requests and limits | **Require Requests and Limits** (`require-requests-limits`) | CPU and memory **requests** and a **memory limit** on every container. **CPU limits are deliberately not required**: they cause throttling (slowing WordPress and llama.cpp) without protecting anything; memory limits are what protect box 1 |
| No privileged containers | **Disallow Privileged Containers** (`disallow-privileged-containers`), within Kyverno's **Pod Security Standards** `baseline` rule set | No privileged containers, host paths or host namespaces (network, PID, IPC). Talos already enforces Pod Security `baseline`; Kyverno adds reporting, CI tests and narrow exceptions |
| Run as non-root | **Require Run As Non-Root** (`require-run-as-nonroot`), from the Pod Security `restricted` set | Containers run as a non-root user. The WordPress image runs Apache as `www-data` on port 8080 (non-root processes can't use port 80) |
| Read-only root filesystem | **Require Read-Only Root Filesystem** (`require-ro-rootfs`) | Containers can't write to their own filesystem. WordPress gets small writable `emptyDir` volumes for `/tmp`, Apache's run and lock directories, PHP sessions and, only if the chosen offload plugin writes uploads locally first, the uploads directory. Backs up the Falco rule on writes to `/var/www/html` |
| Health probes | **Require Pod Probes** (`require-pod-probes`) | Readiness and liveness probes on every long-running workload; Argo Rollouts, the HPA and Kubernetes' own restarts depend on them |
| No NodePorts | **Disallow NodePort** (`restrict-nodeport`), plus a rule blocking `LoadBalancer` Services | Nothing needs them: traffic arrives through the Cloudflare Tunnel at home and through the ALB (created from an Ingress, target type `ip`) on AWS |
| Unique Ingress hosts | **Unique Ingress Host and Path** (`unique-ingress-host-and-path`), which looks up existing Ingresses before admitting a new one | Two Ingresses can't claim the same host and path (e.g. a staging or admin hostname colliding with production) |
| Default-deny networking | A **generate** rule | Every new application namespace gets the Cilium baseline allowances (see [Networking](#networking-cilium-and-hubble)) |

**Where each policy applies strictly:** the project's own workloads (WordPress, the summarizer, the LiteLLM gateway, the staging and seed Jobs) must pass **all** of them. Third-party platform components get narrow **`PolicyException`** resources only where they genuinely need it, for example: Cilium, Falco, local-path-provisioner, the NVIDIA device plugin and (on EKS) the VPC CNI and EBS CSI node agents need privileged access; some upstream images can't run with a read-only filesystem or as non-root. Each exception names the exact namespace and workload and is reviewed like any other change.

**Rollout:** every policy starts in **audit mode**; Policy Reporter's findings go to `#rl-security`; fix or add a justified exception for each; then switch to **enforce**.

- The **Kyverno CLI** (`kyverno test` and `kyverno apply`) runs the same policies in `wp-gitops` CI against every manifest change, so violations fail the pull request before Argo CD ever deploys them. This covers the "policy checks before deploy" role often given to OPA, without a second policy engine.
- **Checkov** scans infrastructure and configuration code in **all four repos'** CI (see below), so insecure settings fail the pull request before anything is applied, built or deployed.

### Infrastructure and configuration scanning (Checkov)
**Checkov** (free, open source, no account needed) is the project's scanner for infrastructure-as-code and configuration. Snyk isn't used: it's a commercial platform whose free tier limits monthly scans, and it would overlap with Checkov (configuration) and Trivy (images and dependencies) without adding coverage.

| Repo | What Checkov scans |
|---|---|
| `wp-infra` | **Terraform** source, plus the **plan** (`terraform show -json` output), which catches problems that only appear once variables and modules are resolved |
| `wp-gitops` | The **rendered Kubernetes manifests** for every overlay (the output of Helm and Kustomize, i.e. exactly what Argo CD would apply), and the Helm values |
| `wp-image` | The **Dockerfile**, the WordPress **Helm chart** |
| `llm-summarizer` | The **Dockerfile**, the summarizer **Helm chart** |
| All four | **GitHub Actions workflows**: actions not pinned to a commit, over-broad `permissions`, untrusted input used in scripts (script injection) |

How it's run:
- **Same version everywhere:** pinned in each repo's `.mise.toml` (installed with `uv`), so local runs and CI match.
- **Fails the pull request** on any failed check that hasn't been explicitly skipped. Skips are written inline (`checkov:skip=<check ID>: <reason>`) or in the repo's `.checkov.yaml`, **always with a reason**, and reviewed like any other change.
- **Results on GitHub:** findings are uploaded as **SARIF** to GitHub's **code scanning**, so they appear inline on pull requests and in each repo's Security tab. Code scanning is free for **public** repos; while the repos are private (without GitHub Advanced Security), Checkov's results show in the CI log and job summary instead, and SARIF upload is switched on when each repo goes public.
- **Overlap with Kyverno is intended:** Checkov checks manifests *before* they're merged, using its own rule set; Kyverno enforces the project's policies *at admission* in the cluster (and its CLI tests the same policies in CI).


### Runtime security and compliance
- **Falco** watches running containers (using its modern eBPF driver) and alerts on suspicious behaviour. Kyverno only checks resources when they're created; Falco covers what happens after. Custom rules for this design:
  - a **shell started** in a WordPress, summarizer or gateway pod, which normally never happens
  - **files written under `/var/www/html`**, since WordPress code is built into the image and `DISALLOW_FILE_MODS` is set
  - **unexpected outbound connections** from the LLM nodes, which should only download model files (the CiliumNetworkPolicies also block these; Falco detects any attempt)
- **Falcosidekick** sends Falco alerts to Alertmanager, Grafana and Slack (`#rl-security`). (On AWS, GuardDuty EKS Runtime Monitoring is the managed alternative; Falco runs the same on both clusters.)
- **kube-bench** audits the cluster against the **CIS Kubernetes Benchmark**, run as a Job with the EKS profile. Reports are saved to `docs/` in `wp-gitops`.
- **Trivy Operator** runs continuously in the cluster, producing CIS compliance reports, vulnerability reports for running images, and configuration audits.
- **Kubescape CLI**, run on demand (monthly at home, once per AWS demo on EKS) from the workstation or the in-cluster CI runners, with **nothing installed in the cluster**: scores each cluster against the **NSA-CISA** and **MITRE ATT&CK** frameworks and analyses **RBAC** for risky permissions, the one area no other tool here covers. Reports are saved in `docs/` in `wp-gitops`. It complements kube-bench rather than replacing it: kube-bench checks node and control-plane configuration directly on the nodes; Kubescape checks workloads and permissions through the Kubernetes API. The in-cluster Kubescape operator is deliberately not used (0.5–1 GB of memory, mostly duplicating Trivy Operator and Falco); see `docs/adr/0003-kubescape-cli-not-operator.md`.

### Stateless operation
- **Custom WordPress image** with plugins and themes built in, built by the `wp-image` repo's CI, pushed to the registry, and deployed by Argo CD.
- **Media uploads offloaded to S3** (S3-Uploads or WP Offload Media, chosen in home plan step 5.1), so WordPress pods need no persistent volume (`persistence.enabled: false`). Not EFS, by decision; see [Media storage: S3, not EFS](#media-storage-s3-not-efs-by-decision).
- **WP-Cron turned off** in WordPress (`DISABLE_WP_CRON`) and run as a **Kubernetes CronJob** instead.
- **Outgoing email through Amazon SES** with an SMTP plugin; each site has its own SES domain identity with DKIM.

### Media storage: S3, not EFS (by decision)
Many WordPress-on-AWS guides, including AWS's own reference architecture, put `wp-content` on **EFS**, a shared network filesystem mounted by every server. This project deliberately doesn't. Media goes to **S3**, and WordPress's code (core, plugins, themes) is **built into the container image**. The reasoning is recorded as an ADR, `docs/adr/0002-s3-media-not-efs.md` in `wp-gitops`.

**Two production patterns, for two kinds of site:**
- **EFS (shared `wp-content`):** traditional or lift-and-shift WordPress on EC2 Auto Scaling groups. It needs no changes to WordPress, so admin-screen plugin installs, caching plugins and plugins that write files all just work. The right choice when site owners install plugins themselves.
- **S3 media + immutable images:** containerised, GitOps-managed WordPress, the approach taken by large platforms such as WordPress VIP and Human Made's Altis (which publishes the open-source S3-Uploads plugin for it). This project is this kind of site.

| | EFS (shared `wp-content`) | S3 media + code in the image (this design) |
|---|---|---|
| What's running | Can change at runtime (admin installs, plugin updates, edited files), so it drifts from Git | **Exactly what's in Git**: a signed, scanned image, pinned by digest |
| Rollback | Rolling back the image doesn't roll back files changed on EFS | Roll back the image version; done |
| Security | A writable code directory is where attackers hide web shells, and they persist across restarts | Read-only root filesystem (Kyverno), Falco alerts on writes to `/var/www/html`; a compromised pod is replaced clean |
| Performance | PHP reads many small files per request, each over the network (needs careful OPcache tuning) | Code is on local disk in the image; media is served by the CDN straight from S3 |
| Cost | ~$0.30/GB-month, plus throughput charges at scale | ~$0.023/GB-month; the CDN serves media without touching the pods |
| Home lab | No EFS at home; would need an NFS server (more load on 8 GB) | The same S3 approach works identically at home |
| Staging, ci, promotion | A shared filesystem per environment, kept in sync somehow | Each environment points at its own bucket |

**What it costs:** no plugin installs from the admin screen (every plugin change is a new image through CI and staging, which is the point here); plugins that write files (some caching, form and backup plugins) need checking or a writable scratch volume; the media offload plugin becomes a key dependency.

**When EFS would be the better choice** (also in the ADR): non-technical editors need to install plugins themselves, or the site relies on plugins that must write to `wp-content` and can't be replaced.

**Offload plugin:** two candidates, compared in home plan step 5.1:
- **S3-Uploads** (Human Made, open source): stores uploads **directly in S3** through a PHP stream wrapper, so nothing is written locally. The best fit for a read-only container.
- **WP Offload Media Lite** (Delicious Brains): writes each upload to the local uploads directory first, then copies it to S3 (and can delete the local copy). Needs a writable `emptyDir` for uploads.

Whichever is chosen must also work with a **custom S3 endpoint**, so the ci tests can use the LocalStack or MinIO stand-ins.

### Backup and recovery
- Automated **RDS backups** with point-in-time recovery, plus a **final snapshot** each time the russetleaf.com demo stack is destroyed.
- Daily **logical backups** of the russetleaf.dev database to S3; see [russetleaf.dev database backups](#russetleafdev-database-backups).
- **S3 versioning**, plus cross-region replication if you need disaster recovery.
- A **restore you have actually tested**.

### Delivery and operations
- **Infrastructure as code** (Terraform or CDK) for the VPC, EKS, Karpenter, RDS, S3 and SQS.
- **GitOps** (Argo CD) for what runs in the cluster.
- **Node autoscaling** with **Karpenter** instead of fixed managed node groups. A small managed node group runs Karpenter itself; Karpenter then creates EC2 nodes directly from two **NodePools**:
  - a **general pool** (spot and on-demand, several instance types) for WordPress and platform services, with **consolidation** to remove idle or underused nodes
  - a **GPU pool** for the self-hosted model, with the `workload=llm` label and `dedicated=llm:NoSchedule` taint, on spot
  - **spot interruption handling** through an SQS queue fed by EventBridge, so pods move before AWS reclaims a spot node
- **Cost visibility** with **OpenCost** (or the free Kubecost EKS bundle, which reads AWS billing data): cost per namespace, workload and node, including the GPU node's share and cost per summary alongside the Bedrock spend.
- **Progressive delivery** with **Argo Rollouts**: new WordPress and summarizer versions go out as canaries (e.g. 10% → 50% → 100%). An analysis step checks Prometheus metrics (error rate, latency) at each stage and **rolls back automatically** if they get worse. The metrics come from **CloudWatch** on AWS (ALB 5xx rate and response time, through Argo Rollouts' CloudWatch provider) and from **ingress-nginx's Prometheus metrics** at home.
- **Metrics, logs and alerts**: Prometheus, **Loki** (logs, collected by Grafana Alloy; see [Logging](#logging-loki--alloy)), Grafana and Alertmanager, including the LLM metrics described below, with every alert routed to **Slack** by site and topic; see [Alerting and notifications](#alerting-and-notifications-slack).
- **Deployment notifications**: Argo CD and Argo Rollouts post syncs, failures, canary steps and rollbacks to `#rl-deploys`.
- **AWS Budgets alerts**, including one on Bedrock spending, in case a bug calls the model in a loop.
- **Tagging**: every AWS resource gets `Project`, `Site`, `Env` and `ManagedBy` tags (plus `Stack=edge|demo` on russetleaf.com) through the AWS provider's `default_tags`, so leftovers can be found and costs split per site.

### WordPress image and Helm chart
The site uses a **custom image built on the official `wordpress` image** and a **small Helm chart of its own** (Deployment/Rollout, Service, Ingress, HPA, PDB, WP-Cron CronJob), both maintained in the `wp-image` repo and released together. The Bitnami WordPress chart isn't used: it only works with Bitnami-format images, and Bitnami cut back its free images in 2025. Owning the chart removes that dependency and keeps every setting visible.

**Where images and charts are hosted:** on **GitHub Container Registry (GHCR)** under the project's GitHub account: `ghcr.io/<github-user>/wp-image` and `ghcr.io/<github-user>/llm-summarizer`, each holding its image and its Helm chart (as an OCI artifact). Each package is linked to the repo whose CI publishes it. **GHCR packages have their own visibility setting, separate from the repo's:** a package stays **private** even after its repo is made public, until its visibility is changed in the package's settings. While packages are private, both clusters need credentials to pull them: an image pull secret for the kubelet, and OCI repository credentials for Argo CD (both from a GitHub token with `read:packages` only, kept in Secrets Manager and synced by External Secrets). Once the packages are public, both can be removed. While packages are private, GitHub's free-plan limits for private packages apply (roughly 500 MB of storage and limited transfer), so either make the packages public early or delete old untagged versions automatically. Why GHCR rather than ECR is recorded in `docs/adr/0004-ghcr-not-ecr.md`.

## Networking: Cilium and Hubble

Both clusters run **Cilium**, so they share one networking story: the same policy types, the same network-flow visibility (**Hubble**), and the same Grafana dashboards and alerts.

### How Cilium runs on each cluster

| | Talos (russetleaf.dev) | EKS (russetleaf.com) |
|---|---|---|
| Mode | **Full CNI**: replaces Talos's default Flannel **and kube-proxy** | **Chaining mode** with the Amazon VPC CNI: the VPC CNI still gives pods their VPC IP addresses; Cilium adds policy enforcement and Hubble on top |
| Key settings | Talos machine config `cluster.network.cni.name: none` and `cluster.proxy.disabled: true`; Cilium `kubeProxyReplacement: true`, `k8sServiceHost: localhost`, `k8sServicePort: 7445` (Talos's KubePrism API endpoint), plus Talos's documented cgroup and capability settings | `cni.chainingMode: aws-cni`, `cni.exclusive: false`, `enableIPv4Masquerade: false`, `routingMode: native`; the VPC CNI's own network policy enforcement stays **off**, so only one component enforces policies |
| Installed by | Terraform (Helm provider) right after the cluster bootstraps, because nothing (including Argo CD) can run without a CNI; Argo CD then manages it from `platform/cilium/` | Terraform (Helm provider) right after the cluster and its managed node group are created; Argo CD then manages it |
| New nodes | Fixed hardware | Karpenter NodePools add the startup taint `node.cilium.io/agent-not-ready=true:NoExecute`, so no pod lands on a new node before Cilium is ready on it |

Terraform installs Cilium only once (later changes are ignored by Terraform, using `lifecycle { ignore_changes }`); from then on, the values in `wp-gitops/platform/cilium/` (with `overlays/home` and `overlays/aws`) are the source of truth, and Cilium upgrades go through Git like everything else.

### Policies: CiliumNetworkPolicies, not plain NetworkPolicies

The project uses **`CiliumClusterwideNetworkPolicy`** and **`CiliumNetworkPolicy`** resources instead of standard Kubernetes `NetworkPolicy`, because they can do three things standard policies can't:
- **Filter outbound traffic by DNS name** (`toFQDNs`). AWS service IP addresses change constantly, so IP-based rules can't say "WordPress may reach S3". FQDN rules can.
- **Use cluster-wide baselines**: one `CiliumClusterwideNetworkPolicy` sets **default-deny** for every application namespace and allows DNS to CoreDNS (with Cilium's DNS proxy turned on, which FQDN rules need).
- **Filter at layer 7** (HTTP methods and paths) where it's worth it, e.g. the summarizer may only call WordPress's REST API.

Each component's policies live in its `base/` (shared by both sites), with per-site differences in the overlays. A summary of the allowed traffic:

| Workload | Allowed inbound | Allowed outbound |
|---|---|---|
| WordPress | From the ingress (ingress-nginx at home; the ALB on AWS), Prometheus | Database (MariaDB in-cluster / RDS Proxy endpoint), Valkey / ElastiCache, and by DNS name only: `*.s3.<region>.amazonaws.com`, `sqs.<region>.amazonaws.com`, `email-smtp.<region>.amazonaws.com`, `sts.<region>.amazonaws.com` |
| Summarizer | Prometheus | WordPress REST API (layer 7: `GET`/`POST` on `/wp-json/*` only), the LiteLLM gateway, `sqs.<region>.amazonaws.com` |
| LiteLLM gateway | Summarizer, staging summarizer, ARC runners (evaluation), Prometheus | llama.cpp, `bedrock-runtime.<region>.amazonaws.com` |
| llama.cpp (LLM nodes) | LiteLLM gateway, Prometheus | The model mirror bucket's S3 endpoint only (init container); nothing else |
| MariaDB (home) | WordPress, the backup Job, Prometheus | `*.s3.<region>.amazonaws.com` (backups) |
| cloudflared (home) | — | Cloudflare's tunnel endpoints (by DNS name), ingress-nginx |

Example (WordPress outbound, simplified):

```yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: wordpress-egress
spec:
  endpointSelector:
    matchLabels:
      app.kubernetes.io/name: wordpress
  egress:
    - toEndpoints:                       # database and cache (home overlay; AWS uses toFQDNs for RDS Proxy/ElastiCache)
        - matchLabels: {app.kubernetes.io/name: mariadb}
        - matchLabels: {app.kubernetes.io/name: valkey}
    - toFQDNs:                           # AWS APIs by name, not IP
        - matchPattern: "*.s3.us-east-1.amazonaws.com"
        - matchName: "sqs.us-east-1.amazonaws.com"
        - matchName: "email-smtp.us-east-1.amazonaws.com"
        - matchName: "sts.us-east-1.amazonaws.com"
      toPorts:
        - ports: [{port: "443", protocol: TCP}, {port: "587", protocol: TCP}]
```

**Guardrails:**
- A **Kyverno generate rule** adds the default-deny baseline's per-namespace allowances when a new application namespace is created, so no namespace is ever left open.
- Policies are tested in CI: rendered and schema-checked with the Cilium CRD schemas (kubeconform), and exercised in the ci kind cluster (which also runs Cilium).
- Falco's "unexpected outbound connection" rule **detects**; the FQDN egress policies **prevent**. Each covers the other's gaps.

### Encryption in transit: Cilium WireGuard
Sensitive connections already use TLS at the application level (WordPress → database, everything → AWS APIs, CloudFront → ALB). On top of that, Cilium's **transparent encryption** encrypts **all pod-to-pod traffic between nodes** with **WireGuard**, with no changes to the applications:

```yaml
encryption:
  enabled: true
  type: wireguard
  nodeEncryption: false        # pod traffic only; node-to-node host traffic is left as is
```

- **Home:** the Talos kernel includes WireGuard, so this is a Cilium setting only. WireGuard encrypts traffic **between** nodes; on the home lab, that's mainly box 1 ↔ box 2 (the gateway ↔ llama.cpp, ARC runners ↔ the gateway). Traffic between pods on the same node never leaves the machine.
- **EKS:** confirm that Cilium's WireGuard encryption is supported in **chaining mode** with the VPC CNI for the Cilium version you install. If it is, turn it on the same way. If not, record that in the service-mesh ADR (below) and rely on the application-level TLS already on every sensitive connection.
- **Cost:** a small amount of CPU for encryption, almost no memory.
- **Check:** `cilium encrypt status` (or `cilium status`) shows WireGuard enabled with a peer for each other node.

### Service mesh (Istio): not used, by decision
The project deliberately has **no service mesh**. The reasoning is recorded as an **architecture decision record (ADR)**, `docs/adr/0001-no-service-mesh.md` in `wp-gitops`:

| What a mesh like Istio would add | How this design already covers it |
|---|---|
| mTLS between services | Cilium WireGuard encryption between nodes, plus TLS on every sensitive connection; per-connection service *identity* checks are the one thing not covered |
| Layer-7 authorization | CiliumNetworkPolicies with layer-7 rules |
| Traffic shifting for canaries | Argo Rollouts (through ingress-nginx and the ALB) for code; the LiteLLM gateway for models |
| Retries, timeouts, circuit breaking | The SQS queue with retries and a dead-letter queue; LiteLLM's retries and fallbacks |
| Per-service request metrics | Hubble HTTP metrics, ingress/ALB metrics, and the apps' own OpenTelemetry metrics |

**Why not:** about four services talk to each other (WordPress, summarizer, gateway, model server), so a mesh's benefits are small. Its costs are not: classic Istio adds a proxy to every pod (roughly 50–100 MB each) plus `istiod` (~300–500 MB), which box 1 can't afford; even Istio's lighter **ambient mode** (no per-pod proxies) adds a few hundred MB, a second policy system overlapping Cilium's, and more to upgrade and debug.

**When this would change** (also in the ADR): many more services calling each other, a requirement to verify service identity on every connection (e.g. a compliance rule), or traffic between several clusters.

**Optional experiment:** try **Istio ambient mode** in a local kind cluster with Cilium (home plan step 6.4), or on EKS during a demo where memory isn't tight (AWS plan step 5.3), and add the findings (memory used, setup issues with Cilium, what it added) to the ADR. Neither site depends on it.

### Hubble: network-flow visibility
- **Hubble** (built into the Cilium agent), **Hubble Relay** (cluster-wide view) and **Hubble UI** are enabled on both clusters. Hubble UI is behind **Cloudflare Access** at home and reached by `kubectl port-forward` on EKS.
- The `hubble` CLI shows live flows, e.g. `hubble observe --verdict DROPPED --namespace wordpress`, which is the first thing to run when a new policy blocks something it shouldn't.

## Database access and credentials

The goal is that **no application holds a long-lived database password** where it can be avoided, and that any password that can't be avoided is **generated by a machine, never seen by a person, and rotated**. The two sites reach that goal differently, because only AWS can let the database trust IAM identities.

### russetleaf.com: IAM authentication through RDS Proxy

```
WordPress pods ──(IAM auth token over TLS)──► RDS Proxy ──(pooled connections, password from Secrets Manager)──► RDS for MariaDB
```

- **WordPress has no database password.** On each new connection, a small **`db.php` drop-in** in the WordPress image creates a short-lived **IAM auth token** (valid 15 minutes) with the AWS SDK for PHP, using WordPress's **Pod Identity** role, and sends it in place of a password over **TLS**. Creating the token is a local signing step, not an AWS API call, and the drop-in reuses a token for several minutes.
- **The IAM check happens at RDS Proxy.** The proxy is set to `iam_auth = REQUIRED` and `require_tls = true`. WordPress's role is allowed `rds-db:connect` on the proxy's `wordpress` user only.
- **Behind the proxy, an ordinary database user.** The proxy logs in to RDS as `wordpress` with a password that Terraform generates and stores in **Secrets Manager**. Only the proxy's own IAM role can read it; no pod, person or Git repo ever holds it. It can be rotated automatically with Secrets Manager's rotation for MariaDB (the proxy picks up the new value).
- **Why a proxy, not IAM straight to RDS:** WordPress opens a new database connection on almost every page request. AWS recommends direct IAM database authentication only for apps making fewer than about 200 new connections per second, and each IAM-checked connection costs a little extra time. RDS Proxy keeps a pool of connections open to the database, so WordPress's connection churn hits the proxy, not the database. It also hides Multi-AZ failovers from WordPress: a failover takes seconds instead of waiting for DNS to change.
- **The master (admin) user:** `manage_master_user_password = true`, so **RDS generates the master password, stores it in Secrets Manager and rotates it**. Nobody chooses or sees it. It's used only by the one-off database setup Job (below) and for break-glass admin work.
- **Creating the `wordpress` user:** the RDS instance is in private subnets, so Terraform (running in GitHub Actions) can't reach it. A small, idempotent **`db-setup` Job** in `overlays/aws` (an Argo CD PreSync hook) reads the master secret and the `wordpress` secret, then runs `CREATE USER IF NOT EXISTS` and `GRANT ... ON wordpress.*`. Because the user lives in the database, it survives demo teardowns in the final snapshot; the Job only does real work on the very first demo.
- **The seed Job** (seeding russetleaf.com from russetleaf.dev) connects the same way as WordPress: IAM token through the proxy, with `rds-db:connect` on its own Pod Identity role.

### Risk: confirm IAM tokens work from PHP first (with a fallback)
The one uncertain part of this design is whether **PHP's MariaDB client (mysqlnd)** can send an IAM auth token to RDS Proxy. The token is sent as a clear-text password over TLS, which some clients only allow with extra settings. This is checked by a **short, early test** (AWS plan step 1.6) before any IAM-specific code is relied on: a small test pod with the WordPress image logs in to the proxy with a token. Until that test passes, the home lab builds only the `password` mode of the `db.php` drop-in.

**If the test fails, the fallback is password login to RDS Proxy with an automatically rotated secret.** It keeps almost every benefit:

| | IAM tokens (preferred) | Fallback: rotated password to the proxy |
|---|---|---|
| App credential | None; a 15-minute token signed by the Pod Identity role | A password, **generated by Secrets Manager**, never seen by a person |
| Proxy auth setting | `iam_auth = REQUIRED` | `iam_auth = DISABLED` (password checked by the proxy) |
| How WordPress gets it | Signs a token itself | **External Secrets** syncs the secret into a Kubernetes Secret |
| Rotation | Not needed (tokens expire) | **Secrets Manager automatic rotation** (e.g. every 30 days), using the **alternating-users** strategy: two database users (`wordpress_a`, `wordpress_b`), so the previous credentials keep working until the next rotation and nothing breaks mid-rotation |
| Picking up a new password | n/a | External Secrets refreshes the Secret; **Reloader** (or an Argo Rollouts restart) restarts WordPress so new pods use it |
| Connection pooling, fast failover, TLS | Yes | Yes (still through RDS Proxy) |
| Chart setting | `database.auth: iam` | `database.auth: password` (the same mode the home lab uses) |

Switching between the two is an **overlay change** in `wp-gitops` (`database.auth` and the credential source) plus the proxy's auth setting in `wp-infra`; the WordPress image supports both.
- **Cost:** RDS Proxy is billed per vCPU of the database instance, about $0.015 per vCPU-hour: roughly **$0.03/hour** for a db.t4g.medium (pennies per demo; about $22/month if it ran 24/7).

### russetleaf.dev: operator-generated passwords

IAM authentication doesn't exist for a self-hosted MariaDB, so the home lab removes the *human* from the password instead:
- **MariaDB Operator generates the passwords** (for the `wordpress` user, the backup user and the root user) into **Kubernetes Secrets**, using its `User` and `Grant` resources. They're random, never typed, never in Git and never in Secrets Manager. (Check the operator version supports generating the Secret; otherwise a small Job creates a random Secret before the `User` is applied.)
- **WordPress reads the generated Secret directly** (same namespace), so there's no External Secrets step for the database.
- **Rotation:** every few months, delete the generated Secret's value and let it be regenerated (or use the operator's rotation feature, if your version has one), then restart WordPress through its Rollout. Done as a scheduled, tested procedure, not by hand.
- **TLS between WordPress and MariaDB:** turn on TLS in MariaDB Operator (with certificates from the operator or cert-manager) and require it for the `wordpress` user, so credentials never cross the network in clear text, even inside the cluster.
- **Staging** has its own MariaDB with its own generated passwords; nothing is shared with production.
- **Stretch goal:** fully passwordless at home with **client certificates** (MariaDB's `REQUIRE X509`, certificates issued by cert-manager). Confirm MariaDB Operator supports certificate-based users before planning on it.

### How it fits the repos

| Repo | What changes |
|---|---|
| `wp-image` | The `db.php` drop-in (IAM token mode) and a chart setting **`database.auth: password | iam`** (default `password`), plus the RDS CA certificate bundle for TLS |
| `wp-infra` | russetleaf.com: RDS Proxy (IAM required, TLS required), the `wordpress` secret and the proxy's role to read it, `manage_master_user_password`, `rds-db:connect` on the WordPress and seed-Job roles |
| `wp-gitops` `overlays/aws` | `database.auth: iam`, the proxy endpoint, the `db-setup` PreSync Job, CiliumNetworkPolicy allowing WordPress → the proxy endpoint (by DNS name) |
| `wp-gitops` `overlays/home`, `overlays/home-staging` | `database.auth: password`, pointing at the MariaDB Operator-generated Secret |
| `wp-gitops` `base/` | Unchanged, except that **no database credential source lives in the base**: each overlay supplies its own |

The WordPress Rollout, Service, HPA and the rest of the base are the same for both sites; only where the credential comes from differs, which is exactly what overlays are for. A `wp-image` release adding the drop-in goes through ci → staging → prod like any other.

**Interview angle:** in the cloud, the database trusts **IAM identities**, so the application has no secret at all; self-hosted, you can't remove every secret, so you **minimise, generate, isolate and rotate** them.

## AI post summaries

### How it works (event-driven)
1. When a post is published or updated, a small **must-use plugin** in the custom WordPress image sends the post ID to an **SQS queue**.
2. **KEDA** watches the queue and scales the **post-summarizer** Deployment from **0 to N pods** based on how many messages are waiting. With nothing to do, no summarizer pods run.
3. The summarizer reads the post through the **WordPress REST API** and sends the text to the **LLM gateway**, which picks a model (see below). The summarizer writes the summary back as the post excerpt or a custom field.
4. Failed messages are retried and, after several attempts, moved to an **SQS dead-letter queue**, which has an alert on it.
5. A daily **CronJob sweep** re-queues any posts still missing a summary, as a backstop.

The summarizer authenticates to WordPress with an **application password** stored in **Secrets Manager** and synced by External Secrets. It reaches SQS through **EKS Pod Identity** (scoped IAM keys at home). **Bedrock model access** must be enabled for each chosen model in the region.

### LLM gateway and model serving
- **LiteLLM** runs in the cluster as the single entry point for all model calls. It gives the summarizer one OpenAI-compatible API, whichever model answers.
- Models behind the gateway:
  - **Amazon Bedrock: Claude Haiku** (default)
  - **Amazon Bedrock: Amazon Nova Lite** (lower-cost alternative)
  - **Self-hosted model** served by **llama.cpp** (OpenAI-compatible server), e.g. a 3B model such as Qwen2.5-3B or Llama 3.2 3B, 4-bit quantized
- The gateway handles:
  - **routing and fallback** (e.g. Bedrock first, the self-hosted model if Bedrock fails or is throttled)
  - **canary splits** for model changes (e.g. send 10% of requests to a new model, then compare quality scores and cost before switching)
  - **rate limits and spending budgets** per app
- The self-hosted model runs on **dedicated LLM nodes** (a Karpenter GPU NodePool on AWS, box 2 at home):
  - The nodes carry the label `workload=llm` and the taint `dedicated=llm:NoSchedule`, so only the model server (plus cluster-wide agents such as node-exporter) runs there.
  - The model server Deployment has a matching **toleration** and **node selector**.
  - Model files are downloaded once by an init container from each site's **model mirror bucket** in S3 (so rebuilds don't depend on Hugging Face) into a volume on the node.
  - The model **stays loaded**, since the node is dedicated to it; KEDA scales only the summarizer.
- On AWS, the LLM nodes come from Karpenter's **GPU NodePool** (e.g. g6.xlarge on spot), using a CUDA build of llama.cpp. At home, it's a **dedicated CPU worker node** (see the home lab section). The same manifests deploy both, with per-environment overlays. On EKS, the **NVIDIA device plugin** (a DaemonSet) lets the model server request the GPU (`nvidia.com/gpu: 1`); the Amazon Linux 2023 NVIDIA AMI already includes the drivers.

### Prompt versioning and evaluation in CI
The summarizer is its own repo, `llm-summarizer`, built to stand alone as an MLOps project (see [Repository structure](#repository-structure-four-repos)).

- The summarizer prompts and model settings live in `llm-summarizer/prompts/`, with a **version number** that the summarizer records alongside each summary.
- A fixed **evaluation set** of 20–30 sample posts lives in `llm-summarizer/evals/`.
- The gateway's **routing settings** (which models run in production, fallbacks, canary weights) are deployment config, so they live in `wp-gitops`. A routing change there should link to the evaluation report that justifies it.
- On every `llm-summarizer` pull request that changes a prompt, the model list being evaluated, or the summarizer code, a GitHub Actions job:
  - generates summaries for the evaluation set **with each model behind the gateway**
  - scores them with **rule-based checks** (length, required keywords, no made-up links) and an **LLM-as-judge** call that grades how faithful each summary is to its post
  - posts the scores **per model** as a **PR comment**, comparing them with the main branch
  - **fails the check** if quality drops below a set threshold
- The job runs on **self-hosted GitHub Actions runners inside the cluster**, managed by **Actions Runner Controller (ARC)**, so it can reach the gateway and the self-hosted model. Runners are **ephemeral** (a fresh pod per job), and jobs from pull requests opened from forks require manual approval, since the repo is public.
- The same gate runs again on a **release tag**. Only if it passes does CI publish the image and Helm chart, attach the evaluation report to the GitHub release, update `MODEL_CARD.md`, and open a version-bump pull request on `wp-gitops`.
- New code rolls out through the Argo Rollouts canary; new models roll out through the gateway's canary split.

### LLM monitoring
The summarizer reports **OpenTelemetry metrics** to Prometheus, labelled by model and prompt version:
- input and output **tokens**
- **latency** per model call
- **errors**, throttling and **gateway fallbacks**
- estimated **cost per summary** and per day
- **queue depth** and age of the oldest message (from SQS)

Prometheus also collects the gateway's metrics (requests, spend and fallbacks per model) and **llama.cpp's built-in metrics** (tokens per second, requests waiting). A **Grafana dashboard** shows these alongside the WordPress metrics, the LLM node's CPU and memory, and the LLM node's cost from OpenCost. **Alertmanager** alerts on error spikes, messages in the dead-letter queue, the self-hosted model being down, and daily Bedrock spend over a set limit, posting them to `#rl-mlops` (and `#rl-critical` for criticals). The Argo Rollouts canary analysis uses the same metrics.

## WordPress monitoring

Prometheus **scrapes** (pulls) metrics from HTTP endpoints; nothing pushes to it. As in most production setups, WordPress is monitored mainly through **exporters around it** (ingress, web server, database, cache, synthetic probes), plus one small **custom metrics plugin** for the few things only WordPress knows. No third-party "WordPress Prometheus" plugin is used: the ones available tend to be small, sparsely maintained, and export generic counts that aren't useful for alerting.

### What's monitored, and how

| Layer | What it tells you | russetleaf.dev (home) | russetleaf.com (AWS) |
|---|---|---|---|
| Requests (rate, errors, latency) | Is the site healthy for visitors? | ingress-nginx metrics | ALB metrics from CloudWatch |
| Web server / PHP | Busy vs idle Apache workers, saturation | **apache_exporter** sidecar reading Apache's `mod_status` page (localhost only) | Same |
| Database | Connections, slow queries, errors | **MariaDB Operator's built-in metrics** (mysqld-exporter sidecar) | RDS and RDS Proxy metrics from CloudWatch |
| Object cache | Hit ratio, memory, evictions | **redis_exporter** (works with Valkey) | ElastiCache metrics from CloudWatch |
| Synthetic checks inside the cluster | Do key pages and the REST API respond correctly? | **blackbox_exporter** probing `/`, `/wp-login.php` and `/wp-json/` | Same |
| WordPress itself | Application health | **Custom metrics plugin** (below) | Same |
| Request traces (optional) | Which code or query is slow | OpenTelemetry PHP → Grafana Tempo (optional; costs memory) | Same, during demos |

(If the image is ever switched from Apache to PHP-FPM + nginx, use **php-fpm_exporter** instead of apache_exporter.)

### The custom metrics plugin
A must-use plugin in `wp-image` (`mu-plugins/metrics/`) exposes a handful of metrics specific to this project:

| Metric | Meaning | Used for |
|---|---|---|
| `wordpress_posts_without_summary` | Published posts still missing an AI summary | The best end-to-end check that the summarizer pipeline works; alert if above zero for an hour |
| `wordpress_cron_overdue_events` | WP-Cron events past their due time | Shows whether the WP-Cron CronJob is running; alert if it keeps growing |
| `wordpress_object_cache_hit_ratio` | From the Redis Object Cache plugin's stats | Warns when caching stops working (database load rises) |
| `wordpress_info{version, php_version, image_version}` | What's actually running | Checking rollouts; spotting version drift between sites |
| `wordpress_posts_published`, `wordpress_comments_pending`, `wordpress_users` | Counts | Dashboards only |

How it's built safely:
- **Never on the public site.** Metrics are served on a **separate internal port** (a second Apache listener, e.g. 9117), not under the public site's URLs. The ingress never routes to that port, and a **CiliumNetworkPolicy** allows only Prometheus to reach it.
- **Cheap to scrape.** Values are cached for about a minute (in Valkey or a WordPress transient), so a scrape doesn't run database queries each time.
- **Shipped with the chart:** the WordPress chart includes the apache_exporter sidecar, a `ServiceMonitor` for both the exporter and the metrics port, and `PrometheusRule` alerts with runbooks (`WordPressPostsMissingSummaries`, `WordPressCronBacklog`, `WordPressObjectCacheHitRatioLow`, `WordPressApacheWorkersSaturated`, `WordPressSyntheticProbeFailing`).
- **Tested:** a unit test for the output format, and a ci test that scrapes the endpoint in the kind cluster.

### Optional: request tracing
OpenTelemetry's PHP auto-instrumentation (a PHP extension plus SDK, added to the image) can send traces of each request (PHP functions, database queries, outgoing calls) to **Grafana Tempo**, linked from Grafana dashboards. It's the most detailed view of slow requests, but Tempo costs memory box 1 doesn't have to spare, so it's **optional**: turn it on for investigations, or during AWS demos where memory isn't tight.

### Cost and memory
$0. The exporters are small (roughly 20–50 MB each); the custom plugin adds nothing measurable. Only the optional Tempo tracing is expensive.

## Logging (Loki + Alloy)

Both sites send all logs to **Grafana Loki**, collected by **Grafana Alloy**, so logs survive pod restarts, evictions and deleted staging runs, and can be searched in Grafana next to the metrics. The reasoning is recorded in `docs/adr/0005-loki-alloy-for-logs.md`.

### Components

| Piece | What it does | Configuration |
|---|---|---|
| **Loki** (single-binary mode) | Stores and indexes logs; queried from Grafana | Index and log data in an **S3 bucket** per site (lifecycle rules matching retention), a small local cache volume; **7-day retention** at home, **14 days** for russetleaf.com (its bucket is in the always-on edge stack, so demo logs can be reviewed afterwards); multi-tenancy off |
| **Grafana Alloy** (DaemonSet, one per node) | Collects every container's logs and sends them to Loki | Adds a **small, fixed label set**: `site`, `env`, `cluster`, `namespace`, `app`, `container`. Everything else (pod name, request IDs) stays in the log line or as structured metadata, because Loki's cost grows with the number of label combinations. Drops noisy debug lines and health-check access logs before sending. Masks obvious secrets (tokens, passwords in query strings) |
| **Talos system logs** (home) | Kubelet, etcd and Talos service logs from the nodes themselves | Talos's machine logging setting sends them as JSON to Alloy on each node (a host port), so node-level problems are searchable too |
| **EKS control plane** (AWS) | API server audit logs | Stay in **CloudWatch Logs** (short retention), as planned; not duplicated into Loki |
| **Log-based alerts** | Alerts on log patterns that metrics can't see | Loki's **ruler** evaluates log queries and sends alerts to the same **Alertmanager → Slack** routing (by `site`, `env` and `team`) |
| **Grafana correlation** | From a metric spike to that pod's logs for the same time window (and to its traces, if Tempo is on) | Loki added as a Grafana data source, with links between dashboards, logs and traces |

Alloy needs to read log files on each node and listen on a host port for Talos's logs, so it gets a narrow **Kyverno `PolicyException`** (host paths and the host port only), like the other node-level agents.

### Log-based alerts (examples)

| Alert | Fires when | Goes to |
|---|---|---|
| `WordPressPHPFatalErrors` | PHP fatal errors appear in WordPress logs more than a few times in 5 minutes | Site channel |
| `SummarizerExceptions` | The summarizer logs repeated unhandled exceptions | `#rl-mlops` |
| `BedrockThrottling` | The gateway logs Bedrock throttling or quota errors | `#rl-mlops` |
| `LokiIngestionErrors` | Alloy can't deliver logs to Loki | Site channel |

Each has a runbook in `docs/runbooks/` and a test of its log query.

### Privacy
Logs can contain visitors' IP addresses and occasionally email addresses. Short retention (7 and 14 days), masking in Alloy, and access to Grafana only through Cloudflare Access (home) or port-forward (AWS) keep that in check. Staging logs come from scrubbed data.

### Cost and memory
- **Money:** a few cents a month per site for the S3 buckets.
- **Memory:** Loki in single-binary mode is roughly 200–500 MB, Alloy about 100–200 MB per node. On box 1 that's tight; keep retention short, drop noise at the collector and keep labels few. Recorded in the box 1 memory budget.

### Slack workspace and channels

| `#rl-mlops` | Evaluation gate results, summarizer releases, Bedrock spend, dead-letter queue, model server down | GitHub, Alertmanager |
| `#rl-costs` | AWS Budgets, Cost Anomaly Detection, weekly OpenCost summary | Amazon Q Developer in chat applications (formerly AWS Chatbot), Alertmanager |
| `#rl-staging` | Staging test runs: started, passed, failed (with results); staging alerts | `staging-test` workflow, Alertmanager (`env=staging`) |

Every message carries a **`site=dev` or `site=com` label** (or a `[dev]` / `[com]` prefix), so the shared channels still show which site it came from.

### How alerts are routed
- **Site and environment labels:** each cluster's Prometheus adds `site` (`dev` or `com`) and `cluster` (`talos-home` or `eks`) to everything it sends, as external labels. Workloads carry an `env` label (`staging` or `prod`), which alerts inherit.
- **Alertmanager routing:**
  - `severity=critical` → `#rl-critical` **and** the site's channel
  - `severity=warning` → the site's channel
  - alerts labelled `team=security`, `team=mlops` or `team=cost` → `#rl-security`, `#rl-mlops` or `#rl-costs`
  - `env=staging` alerts → `#rl-staging` only (never `#rl-critical`)
  - grouped by alert name and site, with repeat intervals (e.g. 4 hours for warnings, 1 hour for criticals) so ongoing problems don't spam the channel
- **Inhibition rules:** when a site is down, its downstream alerts (WordPress errors, summarizer failures, etc.) are suppressed, so the one alert that matters stands out.
- **One Slack app for the clusters:** a custom Slack app (e.g. "russetleaf-bot") with a bot token, used by Alertmanager, Argo CD Notifications, Argo Rollouts, Falcosidekick and Policy Reporter. The token lives in **Secrets Manager** and reaches each cluster through External Secrets; it's never in Git.

### Watching from outside the clusters
A cluster can't report that it's completely down, so two outside checks back up Alertmanager:
- **Dead man's switch:** Alertmanager's always-firing `Watchdog` alert pings a free heartbeat service (e.g. healthchecks.io) every few minutes. If the pings stop (cluster down, Alertmanager broken, home internet out), the heartbeat service posts to `#rl-critical`.
- **External uptime checks** (e.g. UptimeRobot or Better Stack free plans), every few minutes:
  - russetleaf.dev must return 200
  - russetleaf.com must return **either** the live site (200) **or** the offline page (503 with its known text). Either is fine; anything else means the always-on edge is broken.

### AWS and Cloudflare alerts
- **AWS:** CloudWatch alarms (ALB 5xx, RDS CPU/storage/connections, ElastiCache memory), AWS Budgets and Cost Anomaly Detection publish to **SNS** topics, which **Amazon Q Developer in chat applications** forwards to Slack. All of it is defined in `wp-infra` Terraform (an `alerting` module).
- **Cloudflare:** notifications for tunnel health and security events go to a Slack webhook (`#rl-dev-alerts`).

### Demo noise control (russetleaf.com)
- `demo-down` creates an Alertmanager **silence** for russetleaf.com before tearing anything down, then posts "russetleaf.com demo stopped" to `#rl-com-alerts`.
- `demo-up` posts "russetleaf.com demo started" once the site returns 200. CloudWatch alarms are created with the demo stack and deleted with it.

### Alerts as code
- Alert rules are `PrometheusRule` resources in Git (in each component's `base/`, plus the summarizer's chart), tested in CI with **`promtool test rules`**.
- Every alert has `severity`, `summary`, `description` and a **`runbook_url`** pointing to `docs/runbooks/<alert>.md` in `wp-gitops`: what it means, how to check, how to fix.
- **Every alert must be actionable.** If nobody would act on it, it's a dashboard panel, not an alert. A monthly review removes or tunes noisy alerts.
- Alertmanager's routing config lives in `platform/monitoring/` (with `overlays/home` and `overlays/aws` setting the site-specific receivers).

### Cost
**$0.** Slack's free plan, the heartbeat service and the uptime checker's free plans, Amazon Q Developer in chat applications, and SNS at this volume are all free.

## Environments and promotion

Changes never go straight to a live site. Every change to the WordPress image, the summarizer or the shared manifests moves through **local → ci → staging → prod**, and only reaches russetleaf.com after it has run on russetleaf.dev.

**Naming:** "dev" in russetleaf.dev is part of the domain name, not an environment. russetleaf.dev is the home lab's **production** site. Environments are labelled explicitly everywhere (Kubernetes labels, Prometheus external labels, AWS tags) with `env=local|ci|staging|prod`, alongside `site=dev|com`.

### The environments

| Environment | Where it runs | Purpose | When it runs | Cost |
|---|---|---|---|---|
| **local** | Your Ubuntu workstation: Docker Compose, plus a local Kubernetes cluster (kind, or Talos in Docker with `talosctl cluster create`) | Fast build-and-try loop for the image, charts and summarizer; rehearse Talos upgrades and manifest changes | On demand | $0 |
| **ci** | A temporary **kind** cluster inside GitHub Actions, created for each pull request | Install the changed charts and run integration tests against **LocalStack** (local stand-ins for S3, SQS and Secrets Manager) and a **mock LLM** (LiteLLM's mock responses), so no AWS account or model is needed | Minutes per pull request | $0 (GitHub-hosted runners are free for public repos) |
| **staging** | The home cluster, in its own namespaces, at `staging.russetleaf.dev` behind Cloudflare Access | Run each new version against **real** AWS services and real models, with real (scrubbed) content, before production | **On demand only (scale-to-zero):** created for each promotion, deleted when tests finish | ~$0–1/month; ~0.7–1 GB of box 1's memory, only while running |
| **prod (home)** | russetleaf.dev | The live site | 24/7 | see the home lab costs |
| **prod (AWS demo)** | russetleaf.com | The full production design, for demos | On demand | see the AWS costs |

AWS has no separate staging: russetleaf.com is already temporary, its Terraform is checked with `plan`, `terraform test` and Checkov before each demo, and its application versions have already passed home staging and production.

### ci: test clusters in GitHub Actions
- **Charts and images** (`wp-image`, `llm-summarizer`): each pull request creates a kind cluster, installs the chart with the `ci` values (LocalStack endpoints, mock LLM, test credentials), and runs integration tests:
  - WordPress: the site installs and loads, an upload lands in the LocalStack S3 bucket, publishing a post sends a message to the LocalStack SQS queue
  - Summarizer: a queued post gets a (mock) summary written back to WordPress; a failing message ends up in the dead-letter queue
- **Manifests** (`wp-gitops`): pull requests render and validate every overlay (as before), and changes to shared platform components are installed into a kind cluster to check they start.
- **LocalStack note:** LocalStack's free-tier terms have changed over time. If its current terms don't suit, use **MinIO** (S3) and **ElasticMQ** (SQS) instead, with a plain Kubernetes Secret in place of Secrets Manager.

### staging: on-demand, scale-to-zero
Box 1 doesn't have memory to spare for an always-on staging copy, so staging exists **only while it's being tested**:
- **Staging Argo CD Applications** (WordPress, a small MariaDB, the summarizer) are in Git under `overlays/home-staging`, but with **auto-sync off**. When idle, nothing is deployed and staging uses no memory.
- **The `staging-test` workflow** (in `wp-gitops`, on the in-cluster ARC runners, using an Argo CD account limited to the staging project) runs each time a staging version changes:
  1. Syncs the staging Applications and waits until they're healthy.
  2. Runs the **data Job**: copies the latest russetleaf.dev production backup from S3, imports it into the staging MariaDB, and **scrubs personal data** (user emails, commenter names and emails, application passwords) before anything else touches it.
  3. Runs the **smoke-test Job**: the home page and a few posts load, an upload goes to the staging S3 bucket, publishing a post produces a summary through the real gateway and real Bedrock models.
  4. **Soaks** briefly (e.g. 30 minutes), checking Prometheus for errors and crash loops.
  5. Records the results, then **deletes** the staging Applications and their volumes (with cascade), returning staging to zero.
- **Separate everything at runtime:** staging has its own namespaces, MariaDB instance (no Valkey, to save memory), media bucket, SQS queue, Secrets Manager entries and a **LiteLLM key with its own small Bedrock budget**. It shares the gateway and the llama.cpp model with production. Its IAM key can **read** the production backup bucket but write only to staging resources.
- **Alerts:** `env=staging` alerts go only to `#rl-staging`, never to `#rl-critical`.

### How a change is promoted
1. **Pull request** in `wp-image` or `llm-summarizer`: unit tests, the **ci** kind-cluster tests, and (for the summarizer) the evaluation gate on the home runners.
2. **Release:** CI builds, scans, signs and publishes the image and chart, then the bot opens a pull request bumping the version in **`overlays/home-staging`**. It **merges automatically** once `wp-gitops` CI passes.
3. **Staging test:** the merge starts the `staging-test` workflow (above). Results are posted to `#rl-staging`.
4. **Promotion to prod:** if staging passed, the bot opens a pull request bumping the same version in **`overlays/home`** (russetleaf.dev) **and `overlays/aws`** (russetleaf.com), with the staging results and release notes attached. **You review and merge.** If staging failed, the bot posts the failure to `#rl-staging` and `#rl-deploys`, and nothing is promoted.
5. **Production rollout:** Argo CD syncs russetleaf.dev, and the Argo Rollouts canary is the last check. The next russetleaf.com demo deploys the same version.

Infrastructure changes follow the same idea with different tools: Terraform modules are tested with **`terraform test`** in CI, Talos version upgrades are rehearsed on a **local Talos-in-Docker cluster** first, and `envs/home` changes are planned in CI before being applied.

**Kargo (optional, later):** Kargo, a GitOps promotion tool from the makers of Argo CD, can replace the promotion workflows with a visual pipeline (stages, verification, approvals). It's a good portfolio addition, but its controllers are always on, so add it only if box 1 has memory to spare. The workflows above are the lightweight default.

## russetleaf.com between demos

### Requirement
When the EKS demo stack isn't running, **russetleaf.com must still answer** with a simple static page, served by CloudFront, that says the AWS demo is offline and links visitors to **russetleaf.dev**. It must switch to the offline page **automatically** when the stack is destroyed, and back to the live site automatically when the stack comes up, with no manual DNS changes.

### Mechanism: an always-on CloudFront edge with error fallback (recommended)
Split the AWS Terraform into two root modules in `wp-infra`:
- **`envs/aws-edge` (always on, ~$1/month):** the Route 53 hosted zone for russetleaf.com, ACM certificates, the CloudFront distribution, the S3 bucket holding the offline page, the russetleaf.com **media bucket**, the **model mirror bucket**, and the secret header value CloudFront sends to the ALB.
- **`envs/aws` (demo stack):** everything else (VPC, EKS, Karpenter, RDS, ElastiCache, WAF, SQS, ...). The ALB itself is created by the AWS Load Balancer Controller from the WordPress Ingress, and **ExternalDNS** creates the `origin.russetleaf.com` record pointing at it.

The CloudFront distribution is set up like this:

| Setting | Value |
|---|---|
| Default behavior (`*`) | Origin `origin.russetleaf.com` (the ALB), HTTPS only, all HTTP methods |
| `/wp-content/uploads/*` | Origin: the russetleaf.com media bucket (Origin Access Control) |
| `/offline/*` | Origin: the offline-page bucket (Origin Access Control) |
| Custom error responses | **502, 503, 504 → `/offline/index.html`**, returned with status **503** |
| Error caching (minimum TTL) | **10 seconds**, so the live site returns quickly once the demo is up |
| Origin connection timeout / attempts | **2 seconds / 1 attempt**, so the offline page appears in a few seconds instead of ~30 |
| Origin custom header | `X-Origin-Verify: <secret>` (checked by the ALB listener rule) |

How the switch works:
1. **Demo stack down:** `origin.russetleaf.com` doesn't exist, so CloudFront can't reach the origin and gets a 502. The custom error response serves the offline page instead. Visitors see "The AWS demo of this site is offline. Visit russetleaf.dev to see the live site."
2. **Demo stack up:** Argo CD deploys WordPress, the Load Balancer Controller creates the ALB, and ExternalDNS creates `origin.russetleaf.com`. Within a minute or so (the DNS record's TTL plus the 10-second error cache), CloudFront reaches the origin and serves the live site.
3. **Demo stack torn down:** removing the Argo CD Applications deletes the Ingress, so the ALB is removed and ExternalDNS deletes the DNS record (run ExternalDNS with `--policy=sync` so it removes records it created). CloudFront falls back to the offline page again.

Returning **503** (rather than 200) tells search engines the site is temporarily unavailable, so they don't index the offline page as the site's content. If the live site is ever broken during a demo (the ALB returns 5xx), visitors see the same offline page rather than an error.

This also works for any HTTP method (logins and form posts get the offline page too), and needs no health checks or DNS changes outside Kubernetes.

**Alternative: Route 53 failover routing.** A primary record pointing at the demo stack with a Route 53 health check, and a secondary record pointing at the offline page. It works, but it's a worse fit here: the primary record would point at resources that are deleted after every demo, health checks add cost (about $0.50–$2/month each), and DNS caching slows the switch. The CloudFront approach needs neither.

### Keeping russetleaf.com content between demos
Each demo creates a new RDS instance, so content needs a plan:
- **Final snapshot on destroy (recommended):** set `skip_final_snapshot = false` on the RDS instance, and have the next `terraform apply` restore from the most recent snapshot. Posts, summaries and settings carry over. Snapshot storage costs a few cents a month for a site this size.
- **Media is never lost:** the russetleaf.com media bucket lives in `envs/aws-edge`, so uploads survive between demos.
- **Optional: seed from russetleaf.dev.** For the first demo, or to refresh russetleaf.com with the live site's content, run the **seed Job** (`wp-gitops/apps/seed-from-dev/`, an Argo CD Application set to manual sync, AWS only). It:
  1. downloads the latest daily backup of russetleaf.dev from its S3 backup bucket (see [russetleaf.dev database backups](#russetleafdev-database-backups))
  2. imports it into RDS for MariaDB through RDS Proxy, logging in with an IAM auth token like WordPress (same engine, so no conversion is needed)
  3. runs `wp search-replace 'russetleaf.dev' 'russetleaf.com' --all-tables` to fix links and settings
  4. copies the media with `aws s3 sync` from the russetleaf.dev media bucket to the russetleaf.com media bucket

  Its IAM role (Pod Identity) may only read the russetleaf.dev backup and media buckets, write to the russetleaf.com media bucket, and `rds-db:connect` through the proxy. After it runs, russetleaf.com shows the same posts as the live site, and the next final snapshot keeps them.

## Budget home lab that mirrors the AWS design

The full AWS stack costs too much to run 24/7 as a portfolio project. Instead:

- Keep the **complete AWS design in Terraform on GitHub**, with CI, so employers can review it.
- Run **russetleaf.dev all the time on a two-node home Talos cluster**, published through a Cloudflare Tunnel.
- Use **real AWS services where they're cheap** (S3, SQS, Secrets Manager, IAM, Bedrock).
- Bring up **russetleaf.com's full AWS stack only for short demos**, then destroy it. Its always-on CloudFront edge shows an offline page pointing to russetleaf.dev the rest of the time.

### Home hardware
| Node | Hardware | Role |
|---|---|---|
| Box 1 | Intel i3, 8 GB RAM | Talos **control plane**, also runs all workloads except the self-hosted model |
| Box 2 | Intel i3, 8 GB RAM | Talos **worker**, dedicated to the self-hosted model (label `workload=llm`, taint `dedicated=llm:NoSchedule`, set in its Talos machine config) |

Box 2 has about **6.5–7 GB** free for the model. A **3B model** (4-bit) is the best fit: about 2.5–3.5 GB of RAM, and roughly 1–2 minutes per summary on an i3 (depending on its generation and core count). That's fine for a queue handling 10–20 posts a month. A 7–8B model also fits (~5–5.5 GB) with better summaries, at about 3–6 minutes each and little memory to spare.

Box 1 is the tight one: Talos, Cilium and Hubble, Argo CD, monitoring and logging (Prometheus, Loki, Alloy), WordPress and the platform services (Kyverno, KEDA, Falco, OpenCost, LiteLLM and others) come to roughly 6–7 GB of its 8 GB. (Hubble UI can be scaled to zero when not in use.) To keep headroom:
- Let the **ARC runners** tolerate box 2's taint, so evaluation jobs run next to the model (they mostly wait on it anyway).
- Keep **Prometheus retention** short (e.g. 7 days) and scrape every 30–60 seconds rather than 15.
- Set requests and memory limits on everything (Kyverno already requires them), so a busy pod can't starve the others.

The cluster still has a single control plane, so it isn't highly available. That's acceptable for a home lab; the AWS design covers high availability.

### russetleaf.dev database backups
**MariaDB Operator** (not Talos) backs up the russetleaf.dev database. Talos has its own snapshot feature, but it only covers the cluster's internal state (etcd), not application data. The operator's `Backup` resource, deployed by Argo CD from `wp-gitops/platform/mariadb/`, runs a scheduled dump and uploads it to S3.

| Setting | Value |
|---|---|
| Backup type | **Logical** (`mariadb-dump`, plain SQL, gzip-compressed). It can be restored into the home MariaDB **and** into RDS for MariaDB. Physical backups (`mariadb-backup`) can't be restored into RDS. |
| Schedule | Daily at 03:00 |
| Retention | 14 days (the operator's `maxRetention`), plus an S3 lifecycle rule as a safety net |
| Bucket | `russetleaf-dev-db-backups` (example name), created in `wp-infra/envs/home` with the `s3-backups` module: versioning on, encryption on, public access blocked, objects and old versions expire after 30 days |
| Credentials | IAM key allowed only to write to and read from that bucket, kept in Secrets Manager and synced by External Secrets (or a keyless IAM role once the OIDC stretch goal is done) |
| Monitoring | The `Backup` runs as a Kubernetes CronJob, so kube-state-metrics reports its last success. Alertmanager alerts if the last successful backup is more than 26 hours old. |
| Restore test | Monthly: restore the latest backup into a scratch MariaDB instance in the cluster (the operator's `Restore` resource, or a new `MariaDB` that bootstraps from the backup), check the post count, then delete it |
| Cost | Under $1/month (daily dumps of a small site are a few MB each) |

Example `Backup` resource (outline; check field names against the operator version you install):

```yaml
apiVersion: k8s.mariadb.com/v1alpha1
kind: Backup
metadata:
  name: russetleaf-dev-daily
  namespace: wordpress
spec:
  mariaDbRef:
    name: mariadb
  schedule:
    cron: "0 3 * * *"
  maxRetention: 336h            # 14 days
  compression: gzip
  storage:
    s3:
      bucket: russetleaf-dev-db-backups
      prefix: mariadb
      endpoint: s3.us-east-1.amazonaws.com
      region: us-east-1
      accessKeyIdSecretKeyRef:
        name: mariadb-backup-s3     # synced from Secrets Manager by External Secrets
        key: access-key-id
      secretAccessKeySecretKeyRef:
        name: mariadb-backup-s3
        key: secret-access-key
      tls:
        enabled: true
```

**Same engine on both sites:** russetleaf.com uses **RDS for MariaDB**, so russetleaf.dev's backups restore into it directly, with no collation rewrites or MySQL compatibility fixes. Pin the home MariaDB to the **same major version** RDS offers (e.g. 11.4 LTS), so a dump from one always loads into the other.

**Media is backed up separately:** uploads live in russetleaf.dev's S3 media bucket, which has versioning on, so deleted or overwritten files can be recovered from older versions.

Two parts of the AWS design deliberately don't run at home:
- **Karpenter** needs a cloud provider to create nodes; the home nodes are fixed hardware.
- **kube-bench** looks for config files and processes where most Linux distributions keep them, and Talos doesn't, so many checks fail or come back "not applicable". Talos is hardened by default (no shell or SSH, read-only system, API-only management), so the home lab documents how Talos meets the CIS benchmark instead, and relies on Trivy Operator's compliance reports for continuous checks.

## Repository structure (four repos)

The project is split across four Git repositories, by **what each one controls** and **how often it changes**, not by environment. Both clusters (home Talos and AWS EKS) are driven from the same repos.

| Repo | Purpose | Publishes | Who reads or writes it | Changes when |
|---|---|---|---|---|
| **`wp-gitops`** | The **source of truth for Argo CD**: everything that runs on both clusters (WordPress, monitoring, platform services, gateway, model server, summarizer settings), with `overlays/home` and `overlays/aws`. Also the project's **hub** (README, this document, diagrams, reports). | Nothing; it's what Argo CD reads | Both Argo CD instances (read only); bots from `wp-image` and `llm-summarizer` open version-bump pull requests | Config or version changes (often) |
| **`wp-infra`** | All **Terraform**: shared modules, plus root modules for russetleaf.com (`envs/aws-edge`, always on; `envs/aws`, demo stack) and russetleaf.dev (`envs/home`) | Cloud and home infrastructure | Its own CI (the only place with cloud admin permissions), and you, locally | Infrastructure changes (rarely) |
| **`wp-image`** | The **custom WordPress image**: plugins, themes, the SQS must-use plugin | Signed image + SBOM | Its own CI | Plugin, theme or WordPress updates |
| **`llm-summarizer`** | The **standalone MLOps project**: summarizer code, prompts, evaluation set and gate, Helm chart, model card, local demo | Signed image + **Helm chart** (OCI), evaluation reports | Its own CI | Code, prompt or model-evaluation changes |

### Why four repos instead of one
- **Config is kept separate from code** (standard Argo CD practice). Argo CD watches only `wp-gitops`, so building an image never triggers a deploy by accident, and every deploy is a reviewed commit in one place.
- **Permissions stay limited by repo.** Only `wp-infra`'s CI can change cloud infrastructure. The image repos can push images and open pull requests, nothing more. Argo CD only reads.
- **Each repo changes at its own pace**, with its own history, CI and releases.
- **`llm-summarizer` stands on its own** as a CV piece for AI and MLOps roles: it can be understood, tested and deployed without the rest of the project.

### Why Terraform isn't split by environment
The home lab's Terraform creates AWS resources too (S3, SQS, Secrets Manager, Bedrock IAM), and the AWS stack needs the same ones. Two Terraform repos would mean duplicating those modules or making one repo depend on the other. One `wp-infra` repo with **shared modules** and a **separate root module and state per environment** avoids both. Destroying the AWS demo never touches the home lab's state.

- **State:** all three environments store state in the S3 bucket from `bootstrap/`, under separate keys, using Terraform's built-in S3 state locking (`use_lockfile = true`, Terraform 1.10+; no DynamoDB table needed).
- **CI permissions without stored keys:** GitHub Actions authenticates to AWS through **GitHub's OIDC provider**. Pull requests get a read-only *plan* role; merges to `main` get the *apply* role. The Cloudflare API token is a GitHub secret.
- **The home environment needs local network access:** the Talos provider talks to the boxes directly, which GitHub's hosted runners can't reach. Run the first `envs/home` apply from your own machine. After the cluster and ARC are up, later home applies can run on the in-cluster ARC runners.
- **Why the AWS side has two environments:** `envs/aws-edge` holds what russetleaf.com needs even when the demo is down (DNS, CloudFront, the offline page, media), and is never destroyed. `envs/aws` holds the expensive demo stack and is created and destroyed for each demo. Destroying one can never touch the other's state.
- **Tearing down the AWS demo:** delete the Argo CD Applications first (or scale the root app to nothing) so the AWS Load Balancer Controller removes the ALB, ExternalDNS removes `origin.russetleaf.com`, and Karpenter removes its nodes. Otherwise `terraform destroy` can hang on resources Terraform didn't create. `terraform destroy` then takes the final RDS snapshot that the next demo restores from.

### `llm-summarizer`: the standalone MLOps project

```
llm-summarizer/
  src/                      # SQS consumer, content source/sink adapters, OpenAI-compatible model client,
                            #   OpenTelemetry metrics
    adapters/wordpress/     # WordPress REST API adapter (the first of possibly several)
  prompts/                  # versioned prompts + model settings (the version is recorded with each summary)
  evals/
    dataset/                # 20–30 sample posts + reference notes
    scorers/                # rule-based checks + LLM-as-judge prompt
    reports/                # saved results per release, compared across models
  chart/                    # Helm chart: Rollout, KEDA ScaledObject, sweep CronJob, ServiceAccount,
                            #   PrometheusRule alerts, Grafana dashboard ConfigMap
  docker/                   # Dockerfile
  demo/                     # docker compose: sample posts + local model or Bedrock, no Kubernetes needed
  ci/                       # kind config, ci chart values (LocalStack SQS, mock LLM), end-to-end tests
  MODEL_CARD.md             # models evaluated, scores, cost per summary, known limitations
  .github/workflows/        # unit tests; kind end-to-end tests (mock LLM); evaluation gate (on ARC runners);
                            #   on release: gate again, build image and chart, SBOM, scan, sign + attest SBOM, publish,
                            #   open a chart-bump pull request on wp-gitops (staging overlay)
```

Design choices that make it stand on its own:
- **Clear interfaces:** jobs come in from a queue (`{"post_id": ...}`), content is read and written through an **adapter** (WordPress is the first), and models are reached through any **OpenAI-compatible endpoint**. LiteLLM (and Bedrock through it) and llama.cpp both qualify, so the summarizer has no hard dependency on any one provider.
- **Its own Helm chart**, published to an OCI registry with the same version as the image. `wp-gitops` only supplies values (queue URL, gateway URL, scaling limits, IAM role). The chart also ships the summarizer's alerts and Grafana dashboard, so whoever deploys it gets monitoring too.
- **Releases gated on quality:** a release tag runs the evaluation gate first; only a passing release is published, with its evaluation report attached to the GitHub release.
- **Model card:** reviewers see which models were compared (Claude Haiku, Nova Lite and the self-hosted model), the scores, the cost per summary and known limitations, without running anything.
- **Local demo:** `docker compose up` runs it against sample posts, so anyone can try it in minutes.
- **Self-hosted runners:** the evaluation gate runs on ARC runners in the home cluster, registered to this repo, because it needs to reach the gateway and the self-hosted model. Runners are ephemeral, and jobs from fork pull requests need manual approval.

### Where each AI component lives

| AI component | Repo |
|---|---|
| Summarizer code, prompts, evaluation set and gate, model card, Helm chart, dashboard and alerts | `llm-summarizer` |

The self-hosted model isn't a special case: its deployment is ordinary platform config in `wp-gitops`, on a dedicated node defined in `wp-infra`, and its quality is judged in `llm-summarizer` alongside the Bedrock models.

### Release and promotion flow
1. A change is merged in `wp-image` or `llm-summarizer` after its unit tests and **ci** kind-cluster tests pass (for `llm-summarizer`, a release tag such as `v1.4.0`, after the evaluation gate passes).
2. CI builds the image (and chart), generates the SBOM, scans it, signs it with cosign, and pushes it to the registry.
3. The bot opens a pull request on `wp-gitops` that changes only the version in **`overlays/home-staging`**, linking the release notes (and, for the summarizer, the evaluation report). It merges automatically once `wp-gitops` CI (rendering, schema checks, Kyverno policy tests) passes.
4. The `staging-test` workflow creates staging, loads scrubbed data, runs the smoke tests and a short soak, then deletes staging again (see [Environments and promotion](#environments-and-promotion)).
5. If staging passed, the bot opens a pull request bumping the version in **`overlays/home`** and **`overlays/aws`**, with the staging results attached. You review and merge.
6. Argo CD syncs the home cluster. Argo Rollouts runs the canary and rolls back automatically if its checks fail. The AWS overlay uses the same versions, so the next AWS demo deploys exactly what's running at home.

**Bot identity:** use a **GitHub App** (preferred) or a fine-grained personal access token that can only open (and, for staging bumps, auto-merge) pull requests on `wp-gitops`, stored as a secret in `wp-image` and `llm-summarizer`. Argo CD Image Updater is an alternative, but bot pull requests keep every deploy reviewable.

### Who can do what

| Identity | Access |
|---|---|
| `wp-infra` CI | AWS through GitHub OIDC: read-only *plan* role on pull requests, *apply* role on `main`; Cloudflare API token |
| `wp-image` CI | Push to the image registry; cosign keyless signing (GitHub OIDC); pull requests on `wp-gitops` via the bot |
| `llm-summarizer` CI | Push images and charts; cosign keyless signing; pull requests on `wp-gitops` via the bot; evaluation runs on in-cluster ARC runners, which call Bedrock through the gateway |
| Argo CD (both clusters) | Read `wp-gitops` and pull charts and images (public repos and public GHCR packages need no credentials; GHCR packages are private by default, even in public repos, so make them public separately or provide credentials) |
| `staging-test` workflow (ARC runners) | An Argo CD account limited to the staging project (sync and delete staging Applications only); posts to `#rl-staging` |
| Kyverno | Admits only images signed by the `wp-image` and `llm-summarizer` release workflows (cosign keyless: GitHub OIDC issuer `https://token.actions.githubusercontent.com`, subject matching each repo's release workflow on `main` or a tag) and carrying their signed SBOM attestation; verifies upstream publishers' signatures where they sign |

### Making a change that spans repos
Work **infrastructure first, then code, then config**, so nothing is deployed before what it depends on exists. Example: the summarizer needs a new SQS queue.
1. `wp-infra`: add the queue and its IAM permission; merge and apply.
2. `llm-summarizer`: add support for it in code; release.
3. `wp-gitops`: merge the bot's chart-bump pull request and add the new queue URL to the values for each environment.

### Building it from scratch
**russetleaf.dev home lab (once):**
1. `wp-infra/bootstrap`: apply locally to create the Terraform state bucket and the GitHub OIDC roles.
2. `wp-infra/envs/home`: apply locally to create the Talos cluster on both boxes, the Cloudflare tunnel and DNS for russetleaf.dev, and the AWS resources used from home. Save the kubeconfig and talosconfig it produces somewhere safe (not in Git).
3. Install Argo CD once with Helm, then apply `wp-gitops/bootstrap/home`. From then on, Argo CD manages everything else, including itself if you add Argo CD to `platform/`.
4. Add the secrets the cluster needs to AWS Secrets Manager (WordPress admin and application passwords; **not** the database passwords, which MariaDB Operator generates; Cloudflare tunnel token, scoped IAM keys for home until the OIDC stretch goal is done); External Secrets syncs them in.

**russetleaf.com always-on edge (once):**
1. If russetleaf.com is registered outside Route 53, point the domain's name servers at the Route 53 hosted zone after the first apply.
2. `terraform apply` in `wp-infra/envs/aws-edge`. This creates the hosted zone, certificates, CloudFront distribution, offline page and media bucket.
3. Check that russetleaf.com shows the offline page with a link to russetleaf.dev.

**russetleaf.com demo (each time):** run the `demo-up` and `demo-down` workflows in `wp-infra`, which perform these steps:
1. `terraform apply` in `wp-infra/envs/aws`. This creates the stack (restoring RDS from the latest snapshot) and installs Argo CD pointed at `wp-gitops/bootstrap/aws`.
2. Wait for Argo CD to sync. Once ExternalDNS creates `origin.russetleaf.com`, russetleaf.com switches from the offline page to the live site on its own, and the workflow posts "demo started" to `#rl-com-alerts`. Demo.
3. Silence russetleaf.com's alerts in Alertmanager, remove the Argo CD Applications (the ALB and `origin.russetleaf.com` are deleted, and russetleaf.com falls back to the offline page), then `terraform destroy` in `envs/aws`, and post "demo stopped" to `#rl-com-alerts`. Never destroy `envs/aws-edge`.

### Moving from the current repo
The current repo (`private-test-wordpress`) becomes `wp-gitops`:
- Rename the repo on GitHub (GitHub redirects the old URL, but update the `repoURL` in Argo CD anyway).
- Move `helm/wordpress/values.yaml` to `apps/wordpress/base/values.yaml`, and update the `$values` path in the WordPress Application.
- Move `application.yaml` into the app-of-apps structure (`apps/wordpress/` plus `bootstrap/home/`).
- Move this document and the two build plans to `docs/`.
- Before making the repo public, check its history for secrets (e.g. with `gitleaks`).

**Keeping versions current:** enable **Renovate** (or Dependabot) on all four repos, for Helm chart versions, Terraform providers, base images, plugins and GitHub Actions. Each update then arrives as a pull request that goes through the same CI.
